## Headless task approvals

Native headless tasks can ask their live parent TUI to review an exact Bash command when DCG returns `ask`.
Forwarding requires allow policies in both sessions and no other pending approval requirement.
The root must register Bash and resolve its policy to `allow` for that command.
Typical eligible policies are `yolo` or an applicable explicit Bash allow; other deny and restriction checks still apply.
A root prompt or deny decision reports `unavailable` without displaying a dialog. Do not loosen policy merely to enable forwarding.
DCG denies, separate restricted-folder approvals, provider safety checks, and non-Bash prompts retain their existing refusal behavior.

Deny is the default. **Approve once** applies to one prepared invocation and creates no remembered child grant.
Cancellation refuses the request. The runtime revalidates both sessions' policy and authority through final backend dispatch.
Approval remains bound to the exact invocation. Drift refuses execution without silently requesting approval again.
Refusals distinguish `parent_approval_denied`, `parent_approval_cancelled`, and `parent_approval_unavailable`, including sub-reasons.
SDK callers retain typed refusal errors through the tool metadata wrapper.
Caller aborts retain the existing `AbortError` path. The root requests its configured approval notification when enabled.
Other extension UI remains unavailable. RPC and no-host sessions receive no automatic forwarding.

Previously refused calls are terminal. Continuation requires a new call and fresh approval.
Parked and cold-restored tasks receive an eligible approval route from their current live parent.
Revival does not resume refused calls or suspended JavaScript promises.
Plain `--resume` restores the journal, not interrupted operations. Submit a new follow-up for a new review.
Seance sessions never inherit task approval forwarding.

Local dialogs use the existing FIFO. Authorized collaborators can receive and answer before local presentation.
PTY input can also be generated by software; `approved` does not attest a human decision.
For real approvals, peer agents must not send pane input. Human-origin evidence requires separate trusted custody.
There is no per-origin prompt quota. Default Deny and cancellation do not provide prompt-flood containment.

## Extension module imports

`import type`, `export type`, and declarations containing only inline type specifiers do not add runtime dependencies to the legacy extension graph.
Explicit native loader attributes and options retain Bun's loader behavior.
Dynamic import options are evaluated once to select native or ordinary dependency loading.
Ordinary dynamic imports retain dependency remapping, module identity, and reload behavior.
Failed graph preparation remains local to that import; unrelated imports retain their module identity and state.
A file can provide ordinary module exports and `with { type: "file" }` assets without the compatibility hooks intercepting those assets.
Literal native file imports support relative paths, package exports and aliases, file URLs, and dynamic import options.

## Memory backends

The agent supports three mutually-exclusive memory backends, selected via the `memory.backend` setting (Settings → Memory tab, or `~/.omp/config.yml`):

- `off` (default) — no memory subsystem runs.
- `local` — existing rollout-summarisation pipeline; writes `memory_summary.md` and consolidated artifacts under the agent dir.
- `hindsight` — talks to a [Hindsight](https://hindsight.vectorize.io) server (Cloud or self-hosted Docker), retains transcripts every Nth user turn, recalls memories on the first turn of a session, and exposes `retain`, `recall`, and `reflect`.

### Hindsight quickstart

1. Run a Hindsight server (Cloud or `docker run -p 8888:8888 ghcr.io/vectorize-io/hindsight:latest`).
2. Set `memory.backend = "hindsight"` and `hindsight.apiUrl = "http://localhost:8888"` (or your Cloud URL).
3. Optional environment overrides (env wins over settings):
   - `HINDSIGHT_API_URL`, `HINDSIGHT_API_TOKEN` — connection
   - `HINDSIGHT_BANK_ID`, `HINDSIGHT_DYNAMIC_BANK_ID`, `HINDSIGHT_AGENT_NAME` — bank addressing
   - `HINDSIGHT_AUTO_RECALL`, `HINDSIGHT_AUTO_RETAIN`, `HINDSIGHT_RETAIN_MODE` — lifecycle
   - `HINDSIGHT_RECALL_BUDGET`, `HINDSIGHT_RECALL_MAX_TOKENS` — recall sizing
   - `HINDSIGHT_BANK_MISSION`, `HINDSIGHT_DEBUG`

Switching backends mid-session immediately replaces the live backend, memory tools, listeners, and system-prompt context. Existing users with `memories.enabled = true|false` are migrated to `memory.backend = "local"|"off"` exactly once on first launch; afterward, `memory.backend` is the sole runtime selector.
